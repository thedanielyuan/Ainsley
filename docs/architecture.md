# How Ainsley is built

What the app does today and where it lives. The mission is in the [README](../README.md); the guiding principles, commands and coding rules are in [AGENTS.md](../AGENTS.md). Update this file in the same PR as any change to what it describes.

## Features and design

- **Next.js 16** (App Router, Cache Components), Tailwind CSS v4, TypeScript.
- **Ainsley AI.** Students only ever meet Ainsley. The models behind it go by one name, Ainsley AI, in two tiers: *reasoning*, for the tutor, the solvers, the verifier, the answer checker, prerequisite maps and second looks, and *fast*, for quick jobs (naming thinking steps, re-ranking search results, transcribing scans, checking claims, reviewing replies). `src/lib/server/ainsley-ai.ts` is the only place that names the model behind each tier; it also holds the API client and `describeError`, which words a failed request for the student without a model or provider name ("Ainsley is very busy right now"). Asked what it runs on, Ainsley says Ainsley AI and that it doesn't share which models are underneath, without claiming to be built from scratch or denying any particular model (the system prompt's "Who you are").
- **The tutor** runs on the reasoning tier at `effort: "high"` with adaptive thinking, streamed from `src/app/api/chat/route.ts`.
- **Thinking, shown as named steps.** Above each reply, a timeline grows while Ainsley works: each stretch of thinking by name ("Planning a hint for part (b)"), each lookup ("Searched your materials for `osmosis tonicity`", with back-to-back searches folded into "Ran 3 searches"), and a "Working for 12s" row marked by Ainsley's mark at work: every 2 seconds a light glides up one side of the mark, over the top and down the other, and the dot at its heart sparks in the accent as it passes (`WorkingMark` in `src/components/logo.tsx`; with reduced motion the mark rests, drawn whole). When the answer starts the row becomes "Worked for 28s", and when the reply is done the steps fold into that line, which opens them again (`src/components/work-timeline.tsx`). Ainsley's checks of its own math (`check_math`, and the check of each finished reply below) run out of sight and never appear as steps. The reasoning itself stays hidden, since a tutor's plan often holds the answer it is guiding the student toward: `/api/chat` asks for summarized thinking (`display: "summarized"`) and streams the summaries to the browser, which sends each passage to `/api/thought` (`src/lib/server/thought-title.ts`), a short fast-tier call at max effort that names what Ainsley is doing without its results, answers or verdicts. A long think becomes several named steps; a thought that can't be named is left out.
- **Tutoring behaviour** lives in the system prompt at `src/lib/ainsley-prompt.ts`, and the tutoring policy (below) holds Ainsley to the student's attempt first and help that rises one rung at a time.
- **Conversations** are stored in the browser (IndexedDB). Each assistant turn is saved with its thinking blocks and replayed unchanged, so the history sent to the API only ever grows (required for the reasoning tier's preserved thinking, and it keeps the prompt cache warm). The tools and system prompt, the same in every chat, have a cache entry of their own that lasts an hour, so a new chat reads them rather than writing them again; the growing conversation behind them is cached for five minutes.
- **Safety fallbacks:** `fallbacks: "default"` retries a classifier-declined request on the fallback model the API recommends.
- **Courses and materials.** A courses page (`/courses`) lists the student's courses as cards, and each course page shows the course's name, composer and chats, with a slim column beside them (under the composer on narrow screens) holding a Materials row — file count, linked folder, and an Add menu (upload files, link or sync a folder). The row opens the Materials dialog: the linked folder and files in a Name / Size / Details list with search and Add, row menus to ask Ainsley about a file, open the original, rename or delete it, and drag-and-drop to upload. Clicking a file opens its preview beside the list (in its place on phones, with Back), using the same scrolling viewer as the workspace (`course-materials.tsx`). Each course has an icon and color (picked when creating it, or by clicking the icon on its page), and the sidebar lists courses with their recent chats beneath. Hovering a course in the sidebar shows its menu (open, edit, rename, delete) and a + that opens the new-chat screen already in that course; the ⋯ beside the Courses heading opens the courses page, where each card's menu edits or deletes the course. Students add PDFs, slides (.pptx), Word documents, text, or photos of problems when creating the course, in the Materials dialog (Add or drag-and-drop), or straight into the composer (paperclip, drag-and-drop, paste, or the camera on phones). They can also link a folder on their computer (`src/lib/folders.ts`): in Chrome and Edge its handle is kept so the course re-reads it (on opening the course, or Sync in the Add or folder menu) and adds new or changed files; elsewhere the folder is read once from a folder picker. Uploads run four at a time. `src/app/api/materials/route.ts` extracts text (pdf.js via `unpdf`, OOXML via `fflate`), downsizes photos with `sharp`, and stores PDFs and images with the Files API so chats reference them by `file_id`. Photos and scanned PDFs have no text layer, so once one is added its text is transcribed in the background (`/api/materials/transcribe`, `src/lib/server/transcribe.ts`): the fast tier writes out each page as it appears, handwriting included, with math in LaTeX and figures named in brackets, reading a long scan eight pages at a time, four parts at once. Files added before this are transcribed the next time the library loads, and the Materials dialog shows "Reading text…" meanwhile. The library itself (and each original file, for reopening) lives in IndexedDB (`src/lib/library.ts`).
- **Materials first, then the web.** A chat started on a course page is in that course; a chat started with the sidebar's Chat button can be added to one with the "Add course" chip beside the paperclip. A course's chats are listed under it in the sidebar and under Recents on its page (where they can be renamed or deleted), and the sidebar's Recents holds the rest. Sidebar chats show a delete icon on hover (deleting asks first); double-click a title there to rename it. The sidebar's Chat button starts a chat in no course unless an unsent message is waiting on the new-chat screen. Which course a chat is in decides what Ainsley's tools can reach (below).
- **A tool-using agent.** Ainsley decides from what the student is trying to do which tools to use, if any, and chains them (find the problem, find how the course teaches it, then check the answer). "Your tools" in the system prompt maps intents to tools: learning a concept → search; stuck on a problem → find the problem and the course's method, work out a verified solution (`solve_problem`), never its answer on the web; checking work → `evaluate_answer`; any other math it's about to state → `check_math`; tripped up by something earlier → `trace_prerequisites`, then teach the gap from where their course taught it; reviewing, exam prep or practice → `get_course_module`, with each practice question solved before it's asked and set without its answer, then the student's answers marked when they send them; outside or current information → the web; asking for videos, readings or practice → their materials, then the web, then every good option with its link and a recommendation; chat and follow-ups → no lookups. The ten tools, declared in `src/lib/server/tools.ts`:
  - `search_course_materials` — BM25 over page text (transcribed text for photos and scans), then the top 30 keyword matches re-ranked by meaning (`/api/materials/rerank`, `src/lib/server/rerank.ts`): the fast tier keeps up to six that are about what Ainsley searched for, best first, and drops those that only share words with the query. If the re-ranking fails, the keyword order stands. Returns citable `search_result` blocks.
  - `open_course_material` — a whole PDF or photo, or specific pages. Files in the student's other courses open too, so a prerequisite can be taught from the course that taught it (files attached in other chats stay with those chats).
  - `get_course_module` — module retrieval: a whole week, unit, lecture or topic as citable passages (about 25k tokens, shared fairly between its files). Modules are inferred from how the student organizes files: a linked folder's subfolders ("Week 3/"), numbering in names ("Lec05", "wk3 notes"), and the rest grouped by type (problem sets, exams…); the course context outlines files by module (`src/lib/course-modules.ts`).
  - `solve_problem` — verified solutions (`/api/solve`, `src/lib/server/solve.ts`): two reasoning-tier solvers, at high effort with the code execution tool, work the problem independently (the second also confirms each answer by an independent route) and return structured solutions with each final answer as a sympy expression. Each solver also checks its answers against every given in the problem by running code, including givens its method didn't need, and reports whether they all agree: a problem whose givens contradict each other (a speed, time and distance that can't all hold) can't be solved as stated, and comes back "Couldn't solve" with the contradiction rather than an answer from the givens that agree. When both solvers give the same answers, both found the givens consistent and raised no problem with the statement, and there's no answer key, the solution is verified; otherwise a third call, the verifier, compares them by running code, works out any part they disagree on, checks every given and the course's answer key if Ainsley passed one, and marks the solution verified or not verified (or the problem unsolvable as stated). Two solvers rarely write one value the same way (24/5 and 4.8, (x + 1)² expanded or not), so their sympy forms are compared by value, by evaluating them in the app with no model call (`src/lib/answer-agreement.ts`): numbers to floating-point error, expressions in variables at sample points of both signs, sets in any order. Whatever that can't establish counts as a difference and goes to the verifier: a form it can't evaluate (a matrix, a complex number, a function it doesn't know), a rounded decimal against an exact value, a list in another order, an equation against a bare value. Ainsley gets the answers, the steps a student would write, what a complete answer needs, and a problem id; it uses the solution to aim its hints and worked examples, not to hand over. Each call says what the problem is for (`purpose`): one the student is working on, a worked example, or a practice question Ainsley is setting, which the tutoring policy (below) holds to the student's attempt first. Solutions are saved in IndexedDB by problem (course, problem text and answer key) so a problem is solved once (`src/lib/problems.ts`); the timeline shows "Solved the problem · Verified" ("Prepared a practice question" or "Worked out an example" when that's what it's for).
  - `evaluate_answer` — step-by-step answer checking by an independent checker (`/api/evaluate`, `src/lib/server/evaluate.ts`): a separate reasoning-tier call, at high effort, with no stake in the conversation. Given the problem id from `solve_problem`, it starts from that verified solution; otherwise it works the problem out itself. It transcribes each step of the student's working and marks it correct, an error, following from an earlier error (credited as markers do), missing a justification, or unreadable, verifying steps with the code execution tool (sympy, numpy), and returns a structured verdict (structured outputs): what's right, the first error with its likely misconception (plus, when two fit, a question that tells them apart), how confidently it read the work, a hint, and the concepts the problem exercises — what it practices and what it relies on from earlier — with how the work showed each and which one each error is in. Those go into the student's knowledge map (below); when the first error is in a prerequisite, Ainsley also gets the student's record on it across all their courses and where it's taught. Photos and short PDFs on the student's latest message go to the checker too, so it reads their work rather than Ainsley's transcription. The assessment goes back to Ainsley only, which turns it into feedback (confirming what the student wrote first when the reading was unsure); the student sees the verdict ("Partly correct") in the timeline above the reply. The solvers, verifier and checker share one runner for these calls (`src/lib/server/code-agent.ts`).
  - `check_math` — checks the math Ainsley is about to state that the solvers and the answer checker don't cover: a value or single calculation, a step of an explanation, a formula applied to a case, an identity, a property, a hint that states a result, the answer to a quick practice question (`/api/check`, `src/lib/server/check.ts`). Ainsley passes each claim as it will write it, with a sympy form of what it computes and the value it claims, and gets back verified, false with the correct value, or couldn't check. The fast tier, at high effort with the code execution tool and a JSON schema, checks them all: on a benchmark of 40 claims with known answers (a divergent integral, a wrong ODE solution, sympy forms that didn't match their claims among them) it matched the reasoning tier verdict for verdict, in about 5 seconds for a handful of claims where the reasoning tier took 8 and sometimes minutes. A "false" changes what the student is told, so the reasoning tier at high effort takes a second look at any claim the fast tier finds false before the verdict stands; if the fast tier declines or fails, the reasoning tier runs the whole check. It runs out of sight: the timeline shows no step for it, and when a claim can't be verified Ainsley says so in its reply.
  - `trace_prerequisites` — prerequisite remediation across courses (`/api/prerequisites`, `src/lib/server/prerequisites.ts`, `src/lib/prerequisites.ts`). A separate reasoning-tier call (low effort, about 15 seconds) maps what a concept builds on, up to three levels and ten prerequisites, given what Ainsley saw (the problem, the error and its misconception), the student's courses, and their knowledge map so far: concepts already in it keep their names, and their record (from answer checks in any course) weighs how likely each prerequisite is to be the gap. Each prerequisite comes with a quick diagnostic question. The browser adds the map to the knowledge map, then finds where each prerequisite is taught across all the student's courses (keyword search over every course file, re-ranked by meaning, the best passage per course), and gives Ainsley the map: most likely gap first, each with its record, diagnostic, and course, file id and page. The system prompt's "When the gap is earlier" has Ainsley tell a slip from a gap, confirm the gap with the diagnostic before teaching, teach it briefly from the pages where their course taught it (opening and citing another course's file when that's where it was taught), check one practice question with `evaluate_answer`, then return to the original problem. The timeline shows "Traced what “Electric flux” builds on · 5 prerequisites".
  - `show_simulation` — an interactive free-body diagram (with a practice mode in which the student draws the forces and has them checked), vector field explorer or function graph, with sliders, drawn in the reply where Ainsley calls it (`src/lib/simulation/`, `src/components/simulation/`).
  - `web_search` / `web_fetch` — dynamic filtering, with homework-answer sites blocked (up to 8 searches and 4 fetches a request). When a student asks for resources (videos, readings, practice), the system prompt has Ainsley list every good option it found, each linked by title with what it's good for, then recommend where to start and why, from what the student asked for and, in a course, how their materials frame the topic.

  The course tools, solving, answer and math checks, and prerequisite maps run on the browser's side of the loop (`src/lib/agent-tools.ts`, `src/lib/course-tools.ts`), where the library, saved solutions and knowledge map live; the chat engine (`src/lib/use-chat.ts`) runs the tool loop, runs a turn's calls in parallel, and resumes `pause_turn`. Which sources to trust and how to reconcile them with the student's course are in the system prompt.
- **Never wrong about math.** The system prompt's "Getting the math right" has Ainsley state no math as fact until code has checked it: `solve_problem` for any problem it guides the student through, works as an example or sets as practice; `evaluate_answer` for their work; `check_math` for everything else, one-step calculations included. When a check finds a claim false, Ainsley uses the correct value; when one can't settle a claim, fails, or the solvers disagreed, it tells the student "I'm not sure" and what it couldn't check, and it doesn't settle a disputed solution itself (checking steps confirms computations, not the method). After every reply with math (spotted by LaTeX or arithmetic in the text, `containsMath`), the browser sends the reply, the conversation before it and the files on the student's latest message to `/api/audit` (`src/lib/server/audit.ts`, `src/lib/reply-check.ts`): the fast tier lists each claim the reply states as fact, with its sympy form (leaving out questions, the student's own work it quotes, what it marks as uncertain, and judgments about approach), and the math checker above runs them; claims it finds false get the reasoning tier's second look with the reply in view, so a claim the reply doesn't really make is dropped. The check runs in the background, out of sight: nothing shows while it runs, or when every claim checks out. When a claim is false or unchecked, the solvers disagreed on a solution, or the check failed, "Not verified" appears beside "Worked for 28s" and the step list ends with what the check found ("Couldn't verify 2 of 7 claims"; `auditBadge` in `src/lib/math-check.ts`). If a claim is false, Ainsley posts a short correction as soon as the chat is idle: the app sends a one-line user turn of its own ("[Automatic math check…]", since a system message has to follow a user turn) and a system message with each false claim, its correct value and how it was checked, and Ainsley replies with "**Correction:** …". The correction is stored with that request and replayed with it on every later request, so the history stays append-only; it's checked like any reply but never corrected in turn. A check a reload interrupts runs again when the app loads.
- **Knowledge map.** One graph of concepts across all the student's courses, kept in IndexedDB (`src/lib/knowledge.ts`): each concept's name, what it builds on (from prerequisite maps), and where their materials teach it, plus one record per concept per answer check (shown or error, practiced or prerequisite, which course, the misconception behind an error). The same concept is one node whichever course it turns up in, since answer checks and the mapper are given the names already in the map and reuse them (names that differ only in case, punctuation, plurals or word order match too), so an error made in a Calculus chat is on the record when the same concept trips the student up in Physics. A concept's record is Bayesian knowledge tracing over its checks ("likely a gap: errors in 2 of 2 answer checks, in MATH 2551 and PHYS 2212"). The map is for Ainsley, not shown to the student; Settings → Data controls → Learning record clears it. Answers to quick diagnostic questions Ainsley judges itself aren't recorded yet; only answer checks are.
- **Tutoring policy: their attempt first, then help one rung at a time.** Guiding principles 1 and 2 are rules the app applies, not only words in the prompt (`src/lib/tutoring.ts`). For each problem the student works on, the app tracks whether they've attempted it (an `evaluate_answer` check of their work) and the most help they've had, on a ladder: nudge, specific hint, worked step, worked example of a similar problem, full solution. A problem is known from `solve_problem` (keyed by its problem id, even when solving fails), from an answer check, or, when no tool establishes it (Ainsley used only `check_math`, or nothing), from the review of the reply, which says when it was about a problem the student brought and writes that problem out; a later answer check or `solve_problem` on the same problem (matched by its words and numbers) carries its attempts and help over. Before each request the app works out the most help allowed this turn and sends it as a `system` message after the student's message, in the same message as any course context (a system message must follow a user message). With no problem in progress, that message sets the rule for one before Ainsley writes anything, so a problem's first reply is covered: if the message brings a problem, ask for their attempt or plan, with at most a nudge, however they ask (a question about a concept isn't limited). A new problem gets a request for their attempt or plan and at most a nudge; without an attempt, help stops at a specific hint; after one, it rises one rung above the help given so far (first feedback on their work points to where the error is, without saying what's wrong), or two when they're stuck after a real attempt (a second check, or they say they're stuck) or mention an exam within a day; once their answer checks correct, anything goes, though the policy suggests confirming it and offering a similar problem. The results of `solve_problem` and `evaluate_answer` carry the policy too, since they change it mid-turn (a new problem, an attempt recorded). A new problem worked out while a worked example is allowed on the problem in progress is taken to be that example, unless `solve_problem`'s `purpose` says it's the student's to solve: a problem they're working on, or a practice question Ainsley is setting. A practice question becomes a problem the student hasn't attempted, so its result tells Ainsley that its answer and any working wait for theirs, however they ask. Practice questions come without answers however the student asks, as the system prompt and the per-turn message both say: the student sends their answers when they're done, each `evaluate_answer` check records an attempt, and help on any answer that isn't right yet climbs the ladder as usual. Once a detour (a prerequisite, a practice question) is solved, the policy returns to the problem the student left. After each reply, `/api/review` says whether it was about the problem in progress, a new one or neither, and rates the help it gave on the same ladder the evals' judge uses (`src/lib/server/help-review.ts`: the fast tier at high effort, with a JSON schema); the next message waits up to 8 seconds for that review, and a reply that couldn't be rated counts as using what it was allowed. The state is folded from what each reply records (`ChatMessage.tutoring`), so it belongs to its chat and editing or regenerating rewinds it; `decideHelp` is the one place that sets the rung, ready for a learner model to cap it as mastery grows. The review also measures **answer leaks**, replies that state the final answer before an attempt, found by the reviewer and by comparing the math in the reply with the saved answers' sympy forms (`src/lib/answer-leak.ts`: the reply's LaTeX is converted and both are evaluated with the simulations' expression evaluator, allowing for rounding, with values the student has already seen or written left out). In development, each review logs a `[ainsley] tutoring …` line, and leaks and help beyond what was allowed log `[ainsley] answer leak …` and `[ainsley] over-help …`; nothing is blocked.
- **Append-only context.** Course context reaches Ainsley as a mid-conversation `system` message after the student's message (a full outline by module when the link changes, a diff when files change), and the tool set never changes, so earlier turns — thinking blocks included — replay byte-for-byte (`src/lib/course-context.ts`). The tutoring policy's message for the turn joins it in that system message and is stored with the student's message. A deleted file is the one exception: it's replaced with a note, and `drop_block` drops reasoning that depended on it. `/api/chat` also drops page citations into PDFs from replayed text, the same way on every request so the history stays consistent (the API rejects them with "Document not found for page citation"; the stored reply keeps them for display). Changing the tool set or system prompt, as adding module retrieval, answer evaluation, verified solving, prerequisite maps, `check_math`, the tutoring policy's help ladder, and Ainsley AI's identity with `solve_problem`'s `purpose` did, makes older chats lose their earlier hidden reasoning once, through the same `drop_block` setting.
- **Citations.** A cited passage ends in a chip for each site or file. Links Ainsley writes stay links (a list of videos is only useful with them), and those to pages it really found join the reply's sources. File citations open the local original directly at the cited slide or page in the right workspace; web citations open their page in a new browser tab. The Sources action under a reply expands its complete list and cited passages inline in the chat (`src/lib/citations.ts`, `src/components/sources.tsx`).
- **Right workspace.** A tabbed companion, beside chats and the new-chat screen, for attached/course files (course pages and the courses page have none: course files open in the Materials dialog). The top-right workspace button opens it; while it's open, its own Close button (top right of the panel) hides it. Each chat keeps its own tabs for the current visit. The divider supports dragging, arrow keys (Shift for larger steps), Home/End, and double-click to reset; its width is remembered on this device. The panel docks when the available area is at least 880px wide and becomes a native modal drawer on smaller screens, with Escape, backdrop dismissal, and focus restoration. Tabs support arrow keys, Home/End and Delete. Files scroll: PDFs and slides are one column of pages drawn with PDF.js as they come near the view (and released far from it), with selectable text; documents, text files, and the Text view of a PDF or deck scroll through their extracted pages. A single toolbar shows the page in view (type a number to jump), zoom (buttons, pinch or Ctrl-scroll, kept per file), and a menu to open or download the original. Citations scroll an open file to the cited page without reloading it, and expanding, resizing, switching tabs or hiding the panel keeps the reader's place (`workspace-context.tsx`, `workspace-panel.tsx`, `material-preview.tsx`, `pdf-pages.tsx`, `lib/use-paged-scroll.ts`). Menus, tooltips and dialogs opened inside the workspace render inside it, so they also work when it's a modal drawer.
- **Slide rendering.** Opening an existing or newly uploaded PPTX posts its original bytes to `/api/materials/preview`. LibreOffice converts it to PDF with hidden slides included and speaker-note pages excluded, and the server verifies that the page count matches the presentation. PDF.js draws the slides in the browser as they scroll into view. The PDF is cached in IndexedDB by immutable material ID and renderer version, reused across citations and visits, and removed with its material. File-size, ZIP-expansion, page-count, concurrency and conversion-time limits bound the work; macros are rejected, and links to outside files (linked pictures, media or objects) are removed before conversion, so LibreOffice draws the copy PowerPoint embeds beside a linked picture and fetches nothing. Fonts can be substituted when the server does not have the original typeface. These are static slide previews, so animations and video playback are not reproduced.
- **Appearance.** Backgrounds: the chat on #191919 with a lighter #1f1f1f sidebar and a #303030 composer in dark mode (the default), white with a #fafafa sidebar in light mode. The logo is white (black in light mode). Settings → Appearance offers Light, Dark or System (follows the device) and an accent color (purple by default, or blue, green, yellow, orange, pink or white — shown as black in light mode, where white wouldn't show), but not the background. Colors are CSS variables in `globals.css`, switched by `data-theme`/`data-accent` on `<html>`; a small script in `app/layout.tsx` applies the saved choice before the first paint (`lib/appearance.ts`, `lib/use-appearance.ts`). Settings is a popup with grouped sections on the left (Profile, Appearance, Shortcuts, Data controls), rows with their controls on the right, full screen on phones.
- **Layout:** a 256px sidebar with 36px rows (collapsing to a 56px icon rail with hover labels) and the Ainsley wordmark beside the logo at the top, and a 752px-wide, 24px-radius composer, 102px tall when empty. On the new-chat screen, from 640px of chat width the heading sits 0.8 × (half the viewport − 64px, at least 240px) − 118.4px from the top of the window (so the 56px header comes off it) with the composer 28px below; narrower, the heading sits in a centered 450px block and the composer pins to the bottom (`src/components/empty-state.tsx`, a container query on the screen). The home heading asks "What should we study?": as the screen opens, an underline draws itself under "study" and a glint travels along it and across the word; once the glint has passed, the underline fades out over 500ms, leaving just the word, in the heading's own color whatever the accent (with reduced motion there's no underline). In a chat the composer pins to the bottom as a 58px single row (attach, text, course, send), switching to the full layout once the text needs a second line, with "Ainsley is AI and can make mistakes." beneath it.

## Keyboard shortcuts

`Enter` sends, `Shift+Enter` adds a line, `⌘K` searches chats, `⌘⇧O` starts a new chat, `⌘⇧\` toggles the right workspace (Ctrl on Windows/Linux).

## PowerPoint previews

PowerPoint previews need LibreOffice on the app server. Install it with `brew install --cask libreoffice` on macOS or your Linux package manager, or set `SOFFICE_PATH` in `.env.local` to an existing `soffice` executable. The renderer uses a temporary isolated profile, deletes its temporary files, and sends no deck to an external viewer. Hosted installations need a Node server/container with LibreOffice and the fonts used by the presentations; a plain serverless deployment without the converter cannot render PowerPoint previews.

## Tests and evals

`npm run eval` drives the running app with problems that have known answers and with simulated students, and prints a summary table by guiding principle: solver and checker accuracy, final answers given before the student's attempt, answers given with practice questions, help that skips hint rungs, and math stated without a check. It calls Ainsley AI's models (a full run costs about $12 and takes about 10 minutes), so it isn't in CI. When to run it, and how to keep runs few, is in [AGENTS.md](../AGENTS.md#commands); flags, costs and how to read the numbers are in [evals/README.md](../evals/README.md), and `node --test "evals/**/*.test.mjs"` checks its answer key offline.

To check slide conversion against a running app, run `node --test tests/slide-preview.test.mjs` (set `AINSLEY_TEST_URL` for another host). The synthetic deck covers embedded and linked images, sections, hidden slides, reordered slide numbers and invalid-upload handling without modifying the app's library.

`node --test tests/knowledge.test.mjs` checks the knowledge map (matching concept names, merging maps, refusing loops, records across courses) and the shapes of prerequisite maps. It needs no server: Node 24 runs the TypeScript sources directly.

`node --test tests/tutoring.test.mjs` checks the tutoring policy (the ladder, the attempt gate, how help climbs, the state folded from replies, the text Ainsley gets) and the answer-leak check on planted replies. It needs no server either.

`node --test tests/answer-agreement.test.mjs` pins when two solvers' answers count as the same: equal values written differently, and everything that has to stay a difference (rounded values, forms that agree on part of their domain, other shapes and orders, forms it can't evaluate). It needs no server either.

`node --test tests/simulation.test.mjs` pins the math the simulations compute in the browser: the expression language, validation of Ainsley's input, free-body physics, practice-mode checking, vector-field derivatives and field lines, graph ranges, and how simulations sit in a reply. It needs no server either.
