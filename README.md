# Ainsley

A personal tutor for university students. Success is measured by how much better students perform on their own after using it, not by how many questions it answers.

## Run it

```bash
cp .env.example .env.local   # then add your ANTHROPIC_API_KEY
npm install
npm run dev                  # http://localhost:3000
```

PowerPoint previews need LibreOffice on the app server. Install it with `brew install --cask libreoffice` on macOS or your Linux package manager, or set `SOFFICE_PATH` in `.env.local` to an existing `soffice` executable. The renderer uses a temporary isolated profile, deletes its temporary files, and sends no deck to an external viewer. Hosted installations need a Node server/container with LibreOffice and the fonts used by the presentations; a plain serverless deployment without the converter cannot render PowerPoint previews.

## How it's built

- **Next.js 16** (App Router, Cache Components), Tailwind CSS v4, TypeScript.
- **Model:** `claude-opus-5-5` at `effort: "high"` with adaptive thinking, streamed from `src/app/api/chat/route.ts`.
- **Thinking, shown like Grok's.** Above each reply, a timeline grows while Ainsley works: each stretch of thinking by name ("Planning a hint for part (b)"), each lookup ("Searched your materials for `osmosis tonicity`", with back-to-back searches folded into "Ran 3 searches"), and a "Working for 12s" row with a spinner. When the answer starts the row becomes "Worked for 28s", and when the reply is done the steps fold into that line, which opens them again (`src/components/work-timeline.tsx`). The reasoning itself stays hidden, since a tutor's plan often holds the answer it is guiding the student toward: `/api/chat` asks for summarized thinking (`display: "summarized"`) and streams the summaries to the browser, which sends each passage to `/api/thought` (`src/lib/server/thought-title.ts`), a short Claude Haiku 5.5 call at max effort that names what Ainsley is doing without its results, answers or verdicts. A long think becomes several named steps; a thought that can't be named is left out.
- **Tutoring behaviour** lives in the system prompt at `src/lib/ainsley-prompt.ts`.
- **Conversations** are stored in the browser (IndexedDB). Each assistant turn is saved with its thinking blocks and replayed unchanged, so the history sent to the API only ever grows (required for Opus 5.5's preserved thinking, and it keeps the prompt cache warm). The tools and system prompt, the same in every chat, have a cache entry of their own that lasts an hour, so a new chat reads them rather than writing them again; the growing conversation behind them is cached for five minutes.
- **Safety fallbacks:** `fallbacks: "default"` retries a classifier-declined request on Anthropic's recommended model.
- **Courses and materials.** Courses work like Claude projects: a courses page (`/courses`) lists them as cards, and each course page is laid out like a Claude project: its name, composer and chats, with a slim column beside them (under the composer on narrow screens) holding a Materials row — file count, linked folder, and an Add menu (upload files, link or sync a folder). The row opens the Materials dialog, modeled on a Claude project's Context dialog: the linked folder and files in a Name / Size / Details list with search and Add, row menus to ask Ainsley about a file, open the original, rename or delete it, and drag-and-drop to upload. Clicking a file opens its preview beside the list (in its place on phones, with Back), using the same scrolling viewer as the workspace (`course-materials.tsx`). Like ChatGPT projects, each course has an icon and color (picked when creating it, or by clicking the icon on its page), and the sidebar lists courses with their recent chats beneath. Hovering a course in the sidebar shows its menu (open, edit, rename, delete) and a + that opens the new-chat screen already in that course; the ⋯ beside the Courses heading opens the courses page, where each card's menu edits or deletes the course. Students add PDFs, slides (.pptx), Word documents, text, or photos of problems when creating the course, in the Materials dialog (Add or drag-and-drop), or straight into the composer (paperclip, drag-and-drop, paste, or the camera on phones). They can also link a folder on their computer (`src/lib/folders.ts`): in Chrome and Edge its handle is kept so the course re-reads it (on opening the course, or Sync in the Add or folder menu) and adds new or changed files; elsewhere the folder is read once from a folder picker. Uploads run four at a time. `src/app/api/materials/route.ts` extracts text (pdf.js via `unpdf`, OOXML via `fflate`), downsizes photos with `sharp`, and stores PDFs and images with the Files API so chats reference them by `file_id`. Photos and scanned PDFs have no text layer, so once one is added its text is transcribed in the background (`/api/materials/transcribe`, `src/lib/server/transcribe.ts`): Claude Haiku 5.5 writes out each page as it appears, handwriting included, with math in LaTeX and figures named in brackets, reading a long scan eight pages at a time, four parts at once. Files added before this are transcribed the next time the library loads, and the Materials dialog shows "Reading text…" meanwhile. The library itself (and each original file, for reopening) lives in IndexedDB (`src/lib/library.ts`).
- **Materials first, then the web.** A chat started on a course page is in that course; a chat started with the sidebar's Chat button can be added to one with the "Add course" chip beside the paperclip. A course's chats are listed under it in the sidebar and under Recents on its page (where they can be renamed or deleted), and the sidebar's Recents holds the rest. Sidebar chats show a delete icon on hover (deleting asks first); double-click a title there to rename it. The sidebar's Chat button starts a chat in no course unless an unsent message is waiting on the new-chat screen. Which course a chat is in decides what Ainsley's tools can reach (below).
- **A tool-using agent.** Ainsley decides from what the student is trying to do which tools to use, if any, and chains them (find the problem, find how the course teaches it, then check the answer). "Your tools" in the system prompt maps intents to tools: learning a concept → search; stuck on a problem → find the problem and the course's method, work out a verified solution (`solve_problem`), never its answer on the web; checking work → `evaluate_answer`; reviewing, exam prep or practice → `get_course_module`, with each practice question solved before it's asked; outside or current information → the web; asking for videos, readings or practice → their materials, then the web, then every good option with its link and a recommendation; chat and follow-ups → no tools. The seven tools, declared in `src/lib/server/tools.ts`:
  - `search_course_materials` — BM25 over page text (transcribed text for photos and scans), then the top 30 keyword matches re-ranked by meaning (`/api/materials/rerank`, `src/lib/server/rerank.ts`): Claude Haiku 5.5 keeps up to six that are about what Ainsley searched for, best first, and drops those that only share words with the query. If the re-ranking fails, the keyword order stands. Returns citable `search_result` blocks.
  - `open_course_material` — a whole PDF or photo, or specific pages.
  - `get_course_module` — module retrieval: a whole week, unit, lecture or topic as citable passages (about 25k tokens, shared fairly between its files). Modules are inferred from how the student organizes files: a linked folder's subfolders ("Week 3/"), numbering in names ("Lec05", "wk3 notes"), and the rest grouped by type (problem sets, exams…); the course context outlines files by module (`src/lib/course-modules.ts`).
  - `solve_problem` — verified solutions (`/api/solve`, `src/lib/server/solve.ts`): two Opus 5.5 solvers, at high effort with the code execution tool, work the problem independently (the second also confirms each answer by an independent route) and return structured solutions with each final answer as a sympy expression. When both give the same expressions and there's no answer key, the solution is verified; otherwise a third call, the verifier, compares them by running code, works out any part they disagree on, checks the course's answer key if Ainsley passed one, and marks the solution verified or not verified (or the problem unsolvable as stated). Ainsley gets the answers, the steps a student would write, what a complete answer needs, and a problem id; it uses the solution to aim its hints and worked examples, not to hand over. Solutions are saved in IndexedDB by problem (course, problem text and answer key) so a problem is solved once (`src/lib/problems.ts`); the timeline shows "Solved the problem · Verified".
  - `evaluate_answer` — step-by-step answer checking by an independent checker (`/api/evaluate`, `src/lib/server/evaluate.ts`): a separate Opus 5.5 call, at high effort, with no stake in the conversation. Given the problem id from `solve_problem`, it starts from that verified solution; otherwise it works the problem out itself. It transcribes each step of the student's working and marks it correct, an error, following from an earlier error (credited as markers do), missing a justification, or unreadable, verifying steps with the code execution tool (sympy, numpy), and returns a structured verdict (structured outputs): what's right, the first error with its likely misconception (plus, when two fit, a question that tells them apart), how confidently it read the work, and a hint. Photos and short PDFs on the student's latest message go to the checker too, so it reads their work rather than Ainsley's transcription. The assessment goes back to Ainsley only, which turns it into feedback (confirming what the student wrote first when the reading was unsure); the student sees the verdict ("Partly correct") in the timeline above the reply. The solvers, verifier and checker share one runner for these calls (`src/lib/server/code-agent.ts`).
  - `web_search` / `web_fetch` — dynamic filtering, with homework-answer sites blocked (up to 8 searches and 4 fetches a request). When a student asks for resources (videos, readings, practice), the system prompt has Ainsley list every good option it found, each linked by title with what it's good for, then recommend where to start and why, from what the student asked for and, in a course, how their materials frame the topic.

  The course tools, solving and answer checks run on the browser's side of the loop (`src/lib/agent-tools.ts`, `src/lib/course-tools.ts`), where the library and saved solutions live; the chat engine (`src/lib/use-chat.ts`) runs the tool loop, runs a turn's calls in parallel, and resumes `pause_turn`. Which sources to trust and how to reconcile them with the student's course are in the system prompt.
- **Append-only context.** Course context reaches Ainsley as a mid-conversation `system` message after the student's message (a full outline by module when the link changes, a diff when files change), and the tool set never changes, so earlier turns — thinking blocks included — replay byte-for-byte (`src/lib/course-context.ts`). A deleted file is the one exception: it's replaced with a note, and `drop_block` drops reasoning that depended on it. `/api/chat` also drops page citations into PDFs from replayed text, the same way on every request so the history stays consistent (the API rejects them with "Document not found for page citation"; the stored reply keeps them for display). Changing the tool set or system prompt, as adding module retrieval, answer evaluation and verified solving did, makes older chats lose their earlier hidden reasoning once, through the same `drop_block` setting.
- **Citations.** A cited passage ends in a chip for each site or file. Links Ainsley writes stay links (a list of videos is only useful with them), and those to pages it really found join the reply's sources. File citations open the local original directly at the cited slide or page in the right workspace; web citations open their page in a new browser tab. The Sources action under a reply expands its complete list and cited passages inline in the chat (`src/lib/citations.ts`, `src/components/sources.tsx`).
- **Right workspace.** A ChatGPT-style tabbed companion, beside chats and the new-chat screen, for attached/course files (course pages and the courses page have none: course files open in the Materials dialog). The top-right workspace button opens it; while it's open, its own Close button (top right of the panel) hides it. Each chat keeps its own tabs for the current visit. The divider supports dragging, arrow keys (Shift for larger steps), Home/End, and double-click to reset; its width is remembered on this device. The panel docks when the available area is at least 880px wide and becomes a native modal drawer on smaller screens, with Escape, backdrop dismissal, and focus restoration. Tabs support arrow keys, Home/End and Delete. Files scroll: PDFs and slides are one column of pages drawn with PDF.js as they come near the view (and released far from it), with selectable text; documents, text files, and the Text view of a PDF or deck scroll through their extracted pages. A single toolbar shows the page in view (type a number to jump), zoom (buttons, pinch or Ctrl-scroll, kept per file), and a menu to open or download the original. Citations scroll an open file to the cited page without reloading it, and expanding, resizing, switching tabs or hiding the panel keeps the reader's place (`workspace-context.tsx`, `workspace-panel.tsx`, `material-preview.tsx`, `pdf-pages.tsx`, `lib/use-paged-scroll.ts`). Menus, tooltips and dialogs opened inside the workspace render inside it, so they also work when it's a modal drawer.
- **Slide rendering.** Opening an existing or newly uploaded PPTX posts its original bytes to `/api/materials/preview`. LibreOffice converts it to PDF with hidden slides included and speaker-note pages excluded, and the server verifies that the page count matches the presentation. PDF.js draws the slides in the browser as they scroll into view. The PDF is cached in IndexedDB by immutable material ID and renderer version, reused across citations and visits, and removed with its material. File-size, ZIP-expansion, page-count, concurrency and conversion-time limits bound the work; macros are rejected, and links to outside files (linked pictures, media or objects) are removed before conversion, so LibreOffice draws the copy PowerPoint embeds beside a linked picture and fetches nothing. Fonts can be substituted when the server does not have the original typeface. These are static slide previews, so animations and video playback are not reproduced.
- **Appearance.** Backgrounds follow Claude's: the chat on #191919 with a lighter #1f1f1f sidebar and a #303030 composer in dark mode (the default), white with a #fafafa sidebar in light mode. The logo is white (black in light mode). Settings → Appearance offers Light, Dark or System (follows the device) and an accent color (purple by default, or blue, green, yellow, orange, pink or white — shown as black in light mode, where white wouldn't show), but not the background. Colors are CSS variables in `globals.css`, switched by `data-theme`/`data-accent` on `<html>`; a small script in `app/layout.tsx` applies the saved choice before the first paint (`lib/appearance.ts`, `lib/use-appearance.ts`). Settings itself follows Grok's popup: grouped sections on the left (Profile, Appearance, Shortcuts, Data controls), rows with their controls on the right, full screen on phones.
- **Layout** follows Grok's measurements: 256px sidebar with 36px rows (collapsing to a 56px icon rail with hover labels) and the Ainsley wordmark beside the logo at the top, and a 752px-wide, 24px-radius composer, 102px tall when empty. The new-chat screen is placed like Grok's home: from 640px of chat width the heading sits where Grok's does (0.8 × (half the viewport − 64px, at least 240px) − 118.4px from the top of the window, so the 56px header comes off it) with the composer 28px below; narrower, the heading sits in a centered 450px block and the composer pins to the bottom (`src/components/empty-state.tsx`, a container query on the screen). The home heading asks "What should we study?": as the screen opens, an underline draws itself under "study" and a glint travels along it and across the word; once the glint has passed, the underline fades out over 500ms, leaving just the word, in the heading's own color whatever the accent (like Grok's "explore"; with reduced motion there's no underline). In a chat the composer pins to the bottom as a 58px single row (attach, text, course, send), switching to the full layout once the text needs a second line, with "Ainsley is AI and can make mistakes." beneath it.

Keyboard: `Enter` sends, `Shift+Enter` adds a line, `⌘K` searches chats, `⌘⇧O` starts a new chat, `⌘⇧\\` toggles the right workspace (Ctrl on Windows/Linux).

To check slide conversion against a running app, run `node --test tests/slide-preview.test.mjs` (set `AINSLEY_TEST_URL` for another host). The synthetic deck covers embedded and linked images, sections, hidden slides, reordered slide numbers and invalid-upload handling without modifying the app's library.
